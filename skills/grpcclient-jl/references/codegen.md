# Code generation

## protojl

```julia
using ProtoBuf
using gRPCClient        # required first; registers the service codegen hook

protojl(proto_file, proto_search_root, output_dir)
```

- `proto_file`: the `.proto` to compile, absolute or relative to the working directory
- `proto_search_root`: directory used to resolve `import` statements inside the proto
- `output_dir`: where generated Julia files are written

`grpc_register_service_codegen()` is exported and can be called explicitly, but `__init__` already calls it, so `using gRPCClient` is sufficient.

## Generated layout

For a proto declaring `package foo`:

```
output_dir/
  foo/
    foo.jl        # module foo; include("foo_pb.jl"); end
    foo_pb.jl     # message structs, encode/decode methods, and client constructors
```

`foo_pb.jl` opens with the ProtoBuf preamble plus `import gRPCClient`, which is injected only when the proto declares at least one service:

```julia
# Autogenerated using ProtoBuf.jl v1.3.0
# original file: proto/test.proto (proto3 syntax)

import ProtoBuf as PB
import gRPCClient
using ProtoBuf: OneOf
using ProtoBuf.EnumX: @enumx

export TestResponse, TestRequest

struct TestRequest
    test_response_sz::UInt64
    data::Vector{UInt64}
end
PB.default_values(::Type{TestRequest}) = (;test_response_sz = zero(UInt64), data = Vector{UInt64}())
PB.field_numbers(::Type{TestRequest}) = (;test_response_sz = 1, data = 2)
# decode / encode / _encoded_size methods follow
```

The injected service block is delimited by `# gRPCClient.jl BEGIN` and `# gRPCClient.jl END` markers, which is what to grep for when checking whether the hook ran.

## Generated constructor

Each RPC produces exactly this shape, with no option defaults baked in; every option flows through `options...` to `gRPCServiceClient`, so the defaults live in one place:

```julia
TestService_TestRPC_Client(
	host, port;
	TRequest=TestRequest,
	TResponse=TestResponse,
	grpc=gRPCClient.grpc_global_handle(),
	options...
) = gRPCClient.gRPCServiceClient{TRequest, false, TResponse, false}(
	host, port, "/test.TestService/TestRPC";
	grpc=grpc,
	options...
)
export TestService_TestRPC_Client
```

Naming is `{ServiceName}_{RPCName}_Client` and the path is `/{package}.{ServiceName}/{RPCName}`, both derived mechanically, so a symbol can be predicted from the proto without reading the generated file. The constructor is exported when the proto file is namespaced or `always_use_modules` is set; otherwise it is defined without an export.

## Type parameters

```julia
gRPCServiceClient{TRequest, SRequest, TResponse, SResponse}
```

| Parameter | Kind | Meaning |
|---|---|---|
| `TRequest` | Type | Request message type, or `Vector{UInt8}` for a raw payload |
| `SRequest` | Bool | `true` when the request side streams |
| `TResponse` | Type | Response message type, or `Vector{UInt8}` for a raw payload |
| `SResponse` | Bool | `true` when the response side streams |

| RPC variant | Parameters |
|---|---|
| Unary | `{TReq, false, TResp, false}` |
| Server streaming | `{TReq, false, TResp, true}` |
| Client streaming | `{TReq, true, TResp, false}` |
| Bidirectional | `{TReq, true, TResp, true}` |

The streaming booleans come from the proto and select which `grpc_async_request` method applies, so they are not something to change at the call site. Constructing a client by hand is only necessary when no stub exists:

```julia
gRPCClient.gRPCServiceClient{Vector{UInt8}, false, Vector{UInt8}, false}(
    "localhost", 50051, "/foo.MyService/MyRPC",
)
```

## Cross-package types

When a service uses message types imported from another proto package, the generated constructor qualifies the type with its package namespace:

```julia
# service ExtService { rpc ExtRPC(ext_types.ExtRequest) returns (ext_types.ExtResponse) {} }
gRPCClient.gRPCServiceClient{ext_types.ExtRequest, false, ext_types.ExtResponse, false}(...)
```

The prefix comes from `rpc.request_type.package_namespace` and `rpc.response_type.package_namespace`, per message type, not from the RPC or the service. A service can therefore mix a local request type with an imported response type.

## Proto to Julia types

| Proto | Julia |
|---|---|
| `uint32` | `UInt32` |
| `uint64` | `UInt64` |
| `int32` | `Int32` |
| `int64` | `Int64` |
| `float` | `Float32` |
| `double` | `Float64` |
| `bool` | `Bool` |
| `string` | `String` |
| `bytes` | `Vector{UInt8}` |
| `repeated T` | `Vector{T}` |
| `message M` | generated struct |
| `enum E` | `@enumx` enum |
| `oneof` | `OneOf` |

Message constructors are positional and follow proto field declaration order, so `message TestRequest { uint64 test_response_sz = 1; repeated uint64 data = 2; }` is built as `TestRequest(42, UInt64[])`. Field defaults are declared by `PB.default_values`.

A `bytes` field mapping to `Vector{UInt8}` is unrelated to using `Vector{UInt8}` as a whole-message type parameter; see `raw-buffers.md`.
