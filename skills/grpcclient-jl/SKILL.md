# gRPCClient.jl

A Julia gRPC client built on libcurl for HTTP/2 transport, with client stubs generated by ProtoBuf.jl. Version 1.0.4. Requires Julia 1.10, streaming RPC included.

Exported names: `grpc_init`, `grpc_shutdown`, `grpc_global_handle`, `grpc_register_service_codegen`, `grpc_async_request`, `grpc_async_await`, `grpc_sync_request`, `grpc_cancel`, `gRPCCURL`, `gRPCRequest`, `gRPCServiceClient`, `gRPCAsyncChannelResponse`, `gRPCException`, `gRPCServiceCallException`.

## Two rules that silently break everything

1. **`using gRPCClient` must come before `protojl`.** Loading the package registers the service codegen hook in `__init__`. Generate stubs without it loaded and the output contains message structs but no `*_Client` constructors, with no error to tell you.
2. **Generated files are `include`d, not `using`ed.** They are plain scripts, not registered packages.

## Generate stubs

```julia
using ProtoBuf
using gRPCClient        # before protojl, see rule 1

protojl("path/to/service.proto", "proto_search_root", "output_dir")
```

The arguments are the `.proto` file, the directory used to resolve its `import` statements, and the output directory. For `package foo`, output lands in `output_dir/foo/foo_pb.jl` with a thin `output_dir/foo/foo.jl` module wrapper. Read `references/codegen.md` for the generated file layout, the `gRPCServiceClient` type-parameter matrix, cross-package imports, and the proto to Julia type mapping.

## Construct a client

One constructor is generated per RPC, named `{ServiceName}_{RPCName}_Client`, hitting path `/{package}.{ServiceName}/{RPCName}`. A client is a lightweight value: it holds a handle, host, port, path, and options, so construct one per RPC and reuse it.

```julia
using gRPCClient
include("gen/foo/foo_pb.jl")

client = MyService_MyRPC_Client("localhost", 50051; deadline = 30)
```

Connection options, accepted by the constructor and also as per-call keyword overrides to `grpc_sync_request` and `grpc_async_request`, where the per-call value wins:

| Option | Default | Notes |
|---|---|---|
| `secure` | `false` | `true` selects https, `false` selects http |
| `deadline` | `10` | Seconds, covering the whole call from submission including time queued for a concurrency slot. `Inf` disables it. `0` expires immediately; negative, `NaN`, and `-Inf` raise `INVALID_ARGUMENT` |
| `keepalive` | `60` | Seconds; sets both TCP keepalive idle time and probe interval |
| `max_send_message_length` | `4*1024*1024` | Per outgoing message, excluding the 5-byte gRPC frame |
| `max_recieve_message_length` | `4*1024*1024` | Per incoming message. The keyword carries a spelling error, `recieve`, and must be written exactly that way |
| `token` | `nothing` | Sent as `authorization: Bearer <token>` on every request |
| `metadata` | `nothing` | `Dict{String,String}` of extra headers. Per-call metadata merges key by key with client metadata rather than replacing it |

Any other keyword raises `ArgumentError: Invalid field of gRPCConnectionOptions`, which is what a misspelling looks like.

Three further keywords are constructor-only, since they are not connection options and passing them per call raises that same `ArgumentError`:

| Keyword | Default | Notes |
|---|---|---|
| `grpc` | `grpc_global_handle()` | The `gRPCCURL` handle, meaning which connection pool and concurrency limit to use, see `references/concurrency.md` |
| `TRequest`, `TResponse` | the proto types | Set either to `Vector{UInt8}` for raw payloads, see `references/raw-buffers.md` |

Setting `token` and an `authorization` metadata entry together raises `INVALID_ARGUMENT`, since they are the same header; the check is case insensitive. To override a client-level token per call, pass `token = nothing` next to the new metadata.

`grpc_init()` runs automatically when the package loads, so no setup call is needed. `grpc_shutdown()` closes connections and cancels in-flight requests, which is useful under Revise or before exiting.

## Unary RPC

```julia
# Simplest: send and block
response = grpc_sync_request(client, MyRequest(42, UInt64[]))

# Submit now, collect later: lets many requests fly concurrently
reqs = [grpc_async_request(client, MyRequest(i, UInt64[])) for i in 1:10]
for req in reqs
    response = grpc_async_await(client, req)   # returns the decoded response
end

# Out-of-order completion: handle each response as it lands
ch = Channel{gRPCAsyncChannelResponse{MyResponse}}(10)
for (index, request) in enumerate(requests)
    grpc_async_request(client, request, ch, index)   # returns nothing
end
for _ in 1:length(requests)
    cr = take!(ch)                     # fields: index, response, ex
    isnothing(cr.ex) || throw(cr.ex)
    handle(cr.index, cr.response)
end
```

The channel form never throws at submission time; a failed request arrives as a `gRPCAsyncChannelResponse` whose `ex` is set and whose `response` is `nothing`, so always check `ex` before touching `response`.

## Streaming RPC

Requests and responses move through `Channel`s, and the streaming side of the call is chosen by the RPC definition, not by the call site:

| RPC variant | Call shape | `grpc_async_await` |
|---|---|---|
| Client streaming | `grpc_async_request(client, request_c)` | `grpc_async_await(client, req)` returns the single response |
| Server streaming | `grpc_async_request(client, request, response_c)` | `grpc_async_await(req)` raises only, returns no data |
| Bidirectional | `grpc_async_request(client, request_c, response_c)` | `grpc_async_await(req)` raises only, returns no data |

Close your request channel to signal end of stream; the library closes the response channel when the stream ends. Read `references/streaming.md` before writing streaming code: channel ownership, the await asymmetry above, and cancellation of a long-lived stream are all easy to get wrong.

## Errors

```julia
struct gRPCServiceCallException <: gRPCException
    grpc_status::Int      # gRPC status code
    message::String
end
```

The `GRPC_*` status constants are **not** exported. Qualify them (`gRPCClient.GRPC_DEADLINE_EXCEEDED`) or import them explicitly. Available: `GRPC_OK`, `GRPC_CANCELLED`, `GRPC_UNKNOWN`, `GRPC_INVALID_ARGUMENT`, `GRPC_DEADLINE_EXCEEDED`, `GRPC_NOT_FOUND`, `GRPC_ALREADY_EXISTS`, `GRPC_PERMISSION_DENIED`, `GRPC_RESOURCE_EXHAUSTED`, `GRPC_FAILED_PRECONDITION`, `GRPC_ABORTED`, `GRPC_OUT_OF_RANGE`, `GRPC_UNIMPLEMENTED`, `GRPC_INTERNAL`, `GRPC_UNAVAILABLE`, `GRPC_DATA_LOSS`, `GRPC_UNAUTHENTICATED`.

Which call raises matters when writing error handling. `grpc_async_request` throws only for programming errors detectable at submission: a shut-down or uninitialized handle as `FAILED_PRECONDITION`, an invalid deadline as `INVALID_ARGUMENT`, an oversized message as `RESOURCE_EXHAUSTED`. Everything that depends on time or concurrency, meaning deadline expiry, cancellation, transport failures, and server statuses, is raised by `grpc_async_await`. Wrapping only the submission in a `try` block therefore catches almost nothing.

## Symptom to cause

| Symptom | Cause |
|---|---|
| `UndefVarError: MyService_MyRPC_Client` | `protojl` ran without gRPCClient loaded, or the generated file was not `include`d |
| `UndefVarError` on a `GRPC_*` constant | The constants are not exported; qualify with `gRPCClient.` |
| `MethodError` on a keyword named `max_receive_message_length` | The keyword is `max_recieve_message_length` |
| `ArgumentError: Invalid field of gRPCConnectionOptions: x` | Unknown per-call option keyword, most often a misspelling |
| `DEADLINE_EXCEEDED` under load with a healthy server | The 10 second default deadline includes time queued for one of the handle's 16 concurrency slots; see `references/concurrency.md` |
| A client or bidi stream never finishes | The request channel was never closed, so the server is still waiting for end of stream |
| `INVALID_ARGUMENT` mentioning the authorization header | `token` and an `authorization` metadata entry were both set |
| Call hangs forever | `deadline = Inf` with no `grpc_cancel`, which is the documented behavior of that setting |
